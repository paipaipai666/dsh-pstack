# 评审自身的指标

门禁拦住的是「红的东西合不进去」。它拦不住另一个方向：评审看起来很忙、PR 一路绿灯、但什么都没抓到。这一页写的是怎么知道评审到底有没有用，以及为什么只看回滚率会骗人。

## 三种模式

新门禁一律先跑 `observe`，读一周它本应拦住什么，再决定是否 `enforce`。三档在任何时刻都可以切换，切换只改配置，不改代码。

| 模式 | 行为 | 用在哪 |
| --- | --- | --- |
| `enforce` | 拦住：红的问题不落地、不过门禁不开 PR | 所有已观察过的门禁，默认值 |
| `observe` | 只记录：写下「本该拦住什么、会用什么文案」，任务照常继续 | 新加的门禁、新改的检查 |
| `off` | 完全不跑，也不记录 | 明确知道这条检查在当前改动上不适用时 |

两处实现：

- `issue-autosync` 的引擎门禁（重大变更必须有人工审批、窄评审不得改树）由 `AUTOSYNC_GATES` 选档，`enforce` 是默认；写错的取值在加载配置时报错，不会静默降级成 `off`。
- `dsh-pstack` 的第 5 层 `Next DSH (observe)` job 是 CI 侧的 observe：`continue-on-error: true`，它的失败记录的是「下一个 DSH 会让我们红」，不许静默通过。

## 要看什么

每条自动化 PR 都在 PR body 里写了 `- Risk:`、证据（命令 + 退出码 + 输出片段）与评审发现；issue 上有 `auto-sync-done` / `auto-sync-failed` / `needs-human`。这些是原始记录，统计从这里来：

```sh
gh pr list --repo paipaipai666/dsh-pstack --state all --limit 200 \
  --json number,title,state,headRefName,createdAt,mergedAt,closedAt,additions,deletions \
  | node scripts/review-metrics.mjs
```

输出是一张按 `auto/` 前缀分组的表：开出的数量、合并、关闭未合并、合并率、合并耗时中位数，以及按改动规模（≤50 行、51–500 行、>500 行）分开的计数。规模必须分组，否则「自动化合并率 90%」可能只是因为它一直在挑小改动。

同时看四个数：

1. **合并率**（`merged / total`）：太低说明门禁在浪费任务；太高要看下一项。
2. **被拒率**（`rejected / total`）：人工关掉而不合并的比例，通常是「评审没抓到、人抓到了」。
3. **回滚率**（标题以 `Revert` 开头的已合并 PR / 已合并总数）：合进去之后又被撤掉的比例，这是最贵的失败。
4. **合并耗时中位数**：门禁变严会先在这里体现；如果它显著上升而回滚率没降，说明新门禁只是变慢了。

## 为什么这张表不能单独读

- **样本太小**。一周可能只有几个自动化 PR，任何比例都在噪声里；至少攒到 20 个同类样本再比较。
- **任务选择不同**。自动化只接带标签的 issue，天然比人类 PR 更窄、更机械；拿它和全部人类 PR 比是不公平的，只能和「同规模、同类改动」的人类 PR 比。
- **高合并率 + 低回滚率也是「什么都没查」的形状**。一个只会说 LGTM 的评审同样能得到这两个数；所以必须同时看被拒率与人工复核抽样的结论。
- **recall 要分三段**。发现率分「原始提出」「验证后保留」「最终被合入」三档；只看第一档会高估，只看第三档会把「被正确驳回」算成漏报。

## 规则

- 同一个签名（同一类问题、同一处代码）在任务日志里出现两次以上，就必须变成一条检查或一条清单项；不许第三次还靠人眼。
- 一条检查上线前先在 `observe` 里跑满一周；`enforce` 之后如果一周内被绕过两次，先看它拦得对不对，再决定放宽而不是直接关掉。
- 每个季度重新读一次这张表；连续两个季度没有任何一条清单项被触发的检查，要么删掉，要么说明它的触发器写错了。

## 这张表回答不了的问题

它不告诉你评审有没有读懂代码，也不告诉你某条发现是对是错。那需要人工抽样：每周随机抽一个已合并的自动化 PR，按 PR body 里的证据逐条复跑命令，记录「证据成立 / 不成立 / 无法复现」。抽样结果不进 CI，进的是下一版的 `BREAKING-CHECKLIST.md`。
